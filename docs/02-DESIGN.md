## 一、记忆的定义（"Define it" 回应）

赛题挑战一要求队伍正面回答：**在企业环境下，什么是真正有价值的"个人/团队记忆"？** 我们认为这一问题不能用"全都重要"的口径敷衍，而必须做出**取舍**。

### 1.1 候选载体的对比

在企业场景下，"记忆"的候选载体至少有四种：

| 候选载体 | 优势 | 致命缺陷 |
|:---|:---|:---|
| **文档全文记忆**（DocStore + RAG） | 保留原文，召回精准 | 无法处理两份文档互相覆盖；时序不可比 |
| **命令/操作历史**（OpHistory） | 可重放，统计性强 | 无法承载跨人协同的决策；语义为空 |
| **通用知识图谱**（General KG） | 表达关系灵活 | 缺少时序与覆盖语义；无 provenance |
| **决策原子 + 演化谱系**（本设计选择） | 同时承载时序、覆盖、跨源、可执行 | 提取成本高，需 LLM 辅助 |

### 1.2 我们的定义

**企业级记忆 = 带演化谱系、跨源共识度、五维时效衰减的决策原子集合。**

一个决策原子由 7 个字段构成：

```
(subject, predicate, object, timestamp, provenance, confidence, evolution_link)
```

它必须同时满足四个属性，缺一不可：

1. **可时序对比**：能回答"这条决策何时被推翻？"
2. **可覆盖追踪**：能表达"A 决策如何 SUPERSEDES B？"
3. **可跨源对齐**：能判定"群聊 / OKR / 文档说的是不是同一件事？"
4. **可机器执行**：能让 CLI 基于这条决策做拦截或补全。

### 1.3 为什么这种"窄定义"比"宽定义"更有价值

宽定义（"所有员工产出的信息都是记忆"）会导致系统沦为另一个搜索引擎；窄定义（决策原子）使系统能在**关键时刻主动干预**——这正是赛题"产生实际效能"的核心要求。其余形式（文档、命令、聊天记录、KG）作为**辅助来源**接入记忆引擎，但不作为记忆的最小单元。

### 1.4 与现有记忆框架的关系

业界已有 LangMem 等通用记忆框架提供 Thread Context、Semantic Facts、Long-term Archives 三层 primitive，解决"对话型 Agent 如何记住事"。本设计与之的关系是：

| 维度 | LangMem 等通用框架 | 本设计 |
|:---|:---|:---|
| 服务对象 | 单 Agent 单会话 | 多人多源企业组织 |
| 记忆单元 | 自由形式 Fact | 结构化决策原子（七字段） |
| 更新语义 | 覆盖/合并 | SUPERSEDES / REFINES / BRANCHES / GENERALIZES |
| 来源信任 | 单一来源标签 | 六档 provenance 加权仲裁 |
| 跨系统 | 不涉及 | 全源一致性 + 共识度计算 |
| 执行联动 | 无 | OpenClaw 双向钩入 CLI |

**复用策略**：短期 Thread Context 层借鉴 LangMem 的会话窗口管理实现；中长期决策记忆使用本文自研的演化感知架构。这一分工使我们既站在前沿框架的肩膀上，也针对企业决策场景做了不可省略的扩展。

## 二、设计取舍：资源约束下的最优分配

v3.3 的核心设计哲学不是"资源全开就堆料"，而是 **"在有限的 LLM 配额与 API 速率内，把每一次昂贵调用花在刀刃上"**。

| 关键约束 | 设计响应 |
|:---|:---|
| Doubao 配额底层是 TPM（1w 单人 / 3w 小组），派生约 10K calls/day | LLM 仅用于"高价值判断点"：Cold Path 提取、演化判定、Reflect 质量评估、跨系统语义对齐；Hot Path 走规则缓存 + 本地向量，不消耗 LLM 额度 |
| 飞书 API 有调用速率限制 | 事件驱动而非轮询；非关键源（日历、审批）走异步批处理；查询结果 5min TTL 缓存 |
| 演示环境不允许网络抖动 | Hot Path 缓存保底；Live demo + Recorded backup 双轨方案 |
| 跨系统一致性是真实需求 | 全源接入但分权重处理：OKR/审批高权重，日历/会议纪要低权重 |
| 五维遗忘超参难以经验调优 | Doubao 离线辅助校准（每两周一次），不占用在线额度 |

**设计原则的转译**：
- Hot/Cold 双路径不是"加速优化"，而是 **"额度受限下的架构必然性"**——若 Hot Path 也走 LLM，日均请求 50K 次将立刻击穿额度。
- 规则缓存（OPPOSITE_PAIRS 词表）不是"LLM 不稳定时的兜底"，而是 **"省下 30% 额度留给真正需要语义判断的场景"**。
- 跨系统对齐只在精确索引命中后才触发，避免对每条消息都做 5 路 API 扫描。

这一框架使系统在赛事提供的有限资源下可跑通，也使其在真实企业部署时具备**经济可行性**——这是评委会问的关键点。

## 三、系统架构

系统在概念层由**感知-决策-记忆**三环联动构成；下方的五层架构图是这三环的工程实现。

- **感知环**：从飞书全源（消息/OKR/文档/审批/妙记/日历）与 CLI 事件中实时提取决策原子，由处理层的 Cold Path 承担。
- **决策环**：基于 Uncertainty / Consensus / Provenance 进行冲突判定与卡片策略分层（Hard 断言 / Soft 询问 / GHOST 静默），由路由层与处理层共同承担。
- **记忆环**：以三层混合存储承载决策原子的演化、覆盖、衰减与归档；通过 Hot Path 缓存对接 CLI 拦截与决策检索。

三环通过共享的决策原子数据模型联动，构成完整的"提取 → 判定 → 存储 → 反馈 → 再提取"闭环。

```

│  输入层：事件驱动的多源接入（飞书 API 限速友好）                                  │

## 四、七大核心机制

### 机制一：全源跨系统一致性检测

**接入源**：

| 数据源 | API | 提取内容 | 一致性校验点 | 信任权重 |
|:---|:---|:---|:---|:---:|
| 飞书消息 | 开放平台消息事件 | 群聊决策、@确认 | 与 OKR/文档交叉验证 | 1.0 |
| 飞书 OKR | OKR API | 目标描述、关键结果 | 与执行层决策冲突检测 | 0.95 |
| 飞书审批 | 审批流 API | 审批结论、驳回理由 | 与群聊决策覆盖关系 | 0.9 |
| 飞书文档 | 文档变更事件 | 文档中显式决议段落 | 与群聊决策语义对齐 | 0.85 |
| 飞书妙记 | 妙记 API | 会议结论、行动项 | 与群聊/文档交叉验证 | 0.7 |
| 飞书日历 | 日历 API | 里程碑日期、会议结论 | 与决策时间线一致性 | 0.5 |

**一致性检测逻辑（额度敏感版）**：

```
对于每个新提取的决策原子：
  1. 精确索引查询：同 subject + predicate 的历史决策（不消耗 LLM）
  2. 若命中 → 进入 P2 演化判定（消耗 1 次 LLM 调用）
  3. 跨系统扫描（仅当精确索引命中时才触发，节省额度）：
     - 查询 OKR API：是否存在语义等价/冲突的目标？
     - 查询文档 API：是否存在语义等价/冲突的段落？
     - 查询日历 API：时间线是否冲突？
  4. 共识度计算 C = Σ(w_i × match_i) / Σ(w_i)
     （OKR=0.4, 文档=0.3, 群聊=0.2, 日历=0.05, 审批=0.05）
  5. 若跨系统冲突 → 触发跨系统对齐卡片
```

**关键优化**：跨系统扫描只在**精确索引命中**后触发，避免对每条新消息都做 5 路 API 扫描，使日均 API 调用从 ~50K 降至 ~5K。

### 机制二：演化图谱（LLM 主路径 + 词表加速层）

**Doubao 演化判定 Prompt**：

```
[系统] 你是企业决策演化判定专家。

[任务] 判定候选决策与父决策的演化关系。

[父决策]
{parent.subject} {parent.predicate} {parent.object}
来源：{parent.source} │ 时间：{parent.created_at}

[候选决策]
{candidate.subject} {candidate.predicate} {candidate.object}
来源：{candidate.source} │ 时间：{candidate.created_at}

[判定选项]
- ROOT：候选是全新决策，无父节点
- SUPERSEDES：候选与父决策对立，覆盖父决策
- REFINES：候选细化父决策，不覆盖
- GENERALIZES：候选泛化父决策（罕见）
- BRANCHES：候选与父决策并存，无覆盖关系

[输出格式]
{
  "evolution_type": "ROOT|SUPERSEDES|REFINES|GENERALIZES|BRANCHES",
  "confidence": 0.0~1.0,
  "reasoning": "判定理由，不超过50字"
}
```

**OPPOSITE_PAIRS 词表（额度加速层）**：若 (candidate_obj, parent_obj) 命中预定义对立词表（如 "冻结" vs "发布"、"批准" vs "驳回"），直接返回 (SUPERSEDES, 0.99)，跳过 LLM 调用，**估算节省日均 30% 额度**。

### 机制三：Reflect 自改进循环

**流程**：

```
每次 Cold Path 完成提取后：
  1. 将 {候选决策, 父决策, 演化类型, 置信度} 送入 Reflect Agent
  2. Doubao 评估："这个演化判定合理吗？"
     - 检查是否存在更相关的父决策被漏掉
     - 检查演化类型是否与语义一致
     - 检查置信度是否校准
  3. 生成 Reflect Report：
     {
       "quality_score": 0.0~1.0,
       "potential_missed_parent": "dec_xxx|null",
       "suggested_type": "SUPERSEDES|REFINES|...",
       "confidence_calibration": "+0.1|-0.05|0"
     }
  4. 若 quality_score < 0.7：
     - 标记该提取为 "待复核"
     - 将误判模式写入质量档案
  5. 质量档案累积 > 100 条后：
     - Doubao 自动总结"高频误判模式"（离线，不占在线额度）
     - 生成 Prompt 优化建议
     - 下一轮提取时自动注入优化后的上下文
```

**Reflect 触发策略（额度敏感）**：仅对 confidence ∈ [0.5, 0.85] 的边界判定调用 Reflect；高置信度（>0.85）和低置信度（<0.5）直接走快路径（高置信度直接通过、低置信度直接进 HYPOTHESIS），**估算节省日均 40% Reflect 调用**。

**Doubao 额度分配（TPM 1w 单人派生 ≈ 10K calls/day）**：

| 调用场景 | 单次消耗 | 日预算 | 优先级 |
|:---|:---:|:---:|:---:|
| P1 提取（Light） | ~500 tokens | 3K | P0 |
| P2 演化判定（仅命中精确索引时） | ~800 tokens | 3K | P0 |
| Reflect 质量评估（仅边界置信度） | ~1K tokens | 1.5K | P1 |
| 跨系统语义对齐（仅冲突候选） | ~1.2K tokens | 1.5K | P1 |
| 五维遗忘参数优化（离线，每两周一次） | ~2K tokens | <0.5K | P2 |
| **预留缓冲（应对突发流量）** | — | **~0.5K** | — |

**额度耗尽降级**：Doubao 日额度耗尽 → 自动切换至本地轻量模型（7B 量化版）或纯规则匹配，次日 0 点恢复。

### 机制四：Actor-Aware 溯源（六档信任体系）

| provenance | 信任权重 | 来源示例 |
|:---|:---:|:---|
| **USER_STATED** | 1.0 | 用户在群聊中明确说"我决定..." |
| **OKR_SYNCED** | 0.95 | 从飞书 OKR 系统同步的目标 |
| **APPROVAL_PASSED** | 0.9 | 飞书审批流正式通过的决议 |
| **DOC_SYNCED** | 0.85 | 从飞书文档正式段落同步 |
| **MEETING_EXTRACTED** | 0.7 | 从妙记/会议纪要提取 |
| **SYSTEM_INFERRED** | 0.5 | Doubao 从自由对话中推断 |

**冲突仲裁**：低信任来源（≤0.7）的决策默认进入 `HYPOTHESIS` 状态，需高信任来源确认或人工复核才转正。

---

### 机制五：Hot / Cold 双路径

| 维度 | Hot Path | Cold Path |
|:---|:---|:---|
| **延迟目标** | < 200ms | < 3s |
| **核心逻辑** | 本地缓存命中 → 直接返回（**零 LLM 调用**） | Doubao 选择性提取+判定+Reflect |
| **缓存策略** | LRU 缓存，TTL=5min；Cold Path 结果实时写入缓存 | 无缓存，按需计算 |
| **额度消耗** | 0% | 100% |
| **服务占比目标** | ~80% 请求 | ~20% 请求 |
| **降级** | 缓存失效 → 直接放行（不阻塞 CLI） | Doubao 额度耗尽 → 切换本地模型 |

---

### 机制六：P4 策略分层 —— Hard 断言 vs Soft 询问

```
IF conflict_level == HARD:
    → 断言式冲突卡片
ELSE IF conflict_level == SOFT AND uncertainty > 0.7:
    → 询问式确认卡片
ELSE IF conflict_level == SOFT AND uncertainty ≤ 0.7:
    → 静默模式
ELSE:
    → GHOST 级别，仅记录
```

**三态处理**：确认更新 → 覆写+刷新RAG；否认 → 重置 uncertainty+提升权重；24h无反馈 → 降权标记 STALE。

**卡片推送的两道硬性闸门**（在策略分层判定为 Hard / Soft 询问之后、实际推送之前执行）：

```
Gate 1: 打扰预算
  每用户每日卡片推送上限 = 5 次
  超额时：当日剩余卡片仅记录到"待复核队列"，不推送
  预算按 confidence × business_impact 排序，优先推送高价值卡片

Gate 2: 工作时间窗
  仅在飞书日历显示的工作时段推送（默认 9:00-19:00 当地时区）
  非工作时段卡片暂存，次日工作时段开始时批量按优先级推送
  紧急 Hard 冲突（如 CLI 拦截已发生）不受时间窗限制
```

**设计意图**：避免系统沦为"骚扰小红点"。这两道闸门同时也是答辩"如何避免用户疲劳"问题的标准答案。

### 机制七：五维上下文自适应遗忘算法

**核心公式**：

```
λ(t) = λ_base × f_freq × f_consensus × f_semantic × f_uncertainty × f_user_validation
```

**乘性建模动机**：五个因子建模五条**独立的衰减通道**——访问频次、跨源共识、语义中心性、置信不确定性、用户验证反馈。乘性结构表达"任一通道告警都应加速遗忘"，符合"短板效应"直觉。加性结构则会被高分因子掩盖低分因子的告警信号。

**超参校准（离线 LLM 辅助）**：

```
1. 收集历史决策生命周期数据（提取时间 → 归档时间 → 人工评估"是否归档过早/过晚"）
2. 构造校准 Prompt：
   "给定以下 50 条决策的生命周期数据，请分析最优的超参组合，
    使得 P_decay ≥ 75% 且误归档率 ≤ 10%"
3. Doubao 输出建议超参组合
4. 人工审核后写入配置中心
5. 每两周自动重新校准一次（离线，不占用在线额度）
```

**为什么用 LLM 而非梯度回归校准？** 在小样本（< 50 条）场景下，岭回归对噪声敏感且可解释性差；LLM 校准利用语言模型对生命周期模式的先验，给出**带 reasoning 的建议**，便于人工审核。当样本量 > 200 时切换为正则化回归，作为 v4 演进项。

**五级状态机**：ACTIVE → STALE → HYPOTHESIS → GHOST → ARCHIVED。

## 六、三大基准测试 + 量化指标体系

本系统的评测体系**严格对齐赛题三大必测试**（抗干扰、矛盾更新、效能验证），其余指标作为支撑证据。

> **详见 [docs/06-benchmark-design.md](./06-benchmark-design.md)** —— TC001-TC009 完整测试用例 + 评分规则 + fixture 契约 + 双系统对比协议（主架构 vs Baseline RAG）+ 与本节"测试一/二/三"的标签映射。本节保留高层指标设计原则；具体协议、数据规模、跑分入口归 06。

### 6.1 三大主测试（直接对应赛题要求）

#### 测试一：抗干扰记忆召回 — 对应赛题"抗干扰测试"

**协议**：

```
1. 注入 1 条关键决策：
   "Q3 冻结发布"（来源：飞书群聊，provenance=USER_STATED）

2. 在 7 天内向同一群聊注入 N=1000 条无关消息：
   - 30% 日常闲聊与表情
   - 30% 技术杂谈（与决策无关的代码评审、架构讨论）
   - 30% 其他独立决策原子（不同 subject/predicate）
   - 10% 噪声字符与图片消息

3. T+7 天，触发查询事件 D：
   - 飞书端：用户问 "我们 Q3 还能发版吗"
   - CLI 端：用户输入 deploy --env=production

4. 系统应在 200ms 内（Hot Path）召回该关键决策并触发拦截/卡片
```

**指标**：

```
Recall_robust = 召回成功次数 / 测试轮数
```

**目标**：Recall_robust ≥ 90%（10 轮测试容许 1 次漏召）

**支撑机制**：
- Postgres 精确索引（subject + predicate 倒排）保证关键词匹配召回
- Qdrant 语义向量保证近义词触发也能召回
- 五维遗忘公式中 f_freq 项保证即使一周未访问，关键决策不被错误归档（f_consensus=0.2 也压低 λ）

---

#### 测试二：矛盾更新覆写准确率 — 对应赛题"矛盾更新测试"

**协议**：

```
1. 输入指令 A："周报每周五发给张三"
2. 时间间隔 t ∈ {1min, 1h, 1d, 7d} 后输入指令 B：
   "不对，以后周报发给李四"
3. 系统应：
   a. 识别 (subject=周报, predicate=SEND_TO) 维度的冲突
   b. 判定 B SUPERSEDES A
   c. 将 A 状态置 ARCHIVED，B 置 ACTIVE
   d. 后续查询 "周报发给谁" 时，仅返回 B
```

**指标**：

```
Acc_supersede = 正确覆写次数 / 矛盾对总数
```

**目标**：Acc_supersede ≥ 95%

**边界情形测试**（必须覆盖以证明鲁棒性）：

| 边界情形 | 期望行为 |
|:---|:---|
| **跨源矛盾**：群聊说 A、文档写 B | 按 provenance 信任权重仲裁；若同源则按时序仲裁 |
| **时序错乱**：B 先收到、A 后收到（事件乱序） | 按 logical timestamp（消息原始时间戳）仲裁，而非接收时间 |
| **软冲突**：A "主要发给张三" / B "也抄送李四" | 判 REFINES 而非 SUPERSEDES，A 保持 ACTIVE |
| **多跳覆盖**：A → B（SUPERSEDES）→ C（SUPERSEDES B） | A、B 均为 ARCHIVED，仅 C 为 ACTIVE，演化树完整 |

---

#### 测试三：操作效能对比 — 对应赛题"效能指标验证"

效能验证从两个维度展开：**时间维度**（决策对齐耗时）与**操作维度**（步数 / 字符数对比）。两个维度共同回应赛题"50 字符 → 10 字符"式的提效叙事，但全部聚焦在决策一致性场景内。

**3.1 时间维度：跨系统对齐效能**

| 场景 | 人工耗时 | 系统耗时 | 提效比 |
|:---|:---:|:---:|:---:|
| 翻查 OKR + 文档 + 群聊确认是否冲突 | ~30 min | ~30 s | **60×** |
| 历史决策溯源（追问"这事去年是怎么定的"） | ~15 min | ~5 s | **180×** |
| 跨部门决策对齐（3 人异步会议） | ~2 hours | ~2 min | **60×** |

```
E_align = T_manual / T_system
```

**目标**：E_align ≥ 60×

**3.2 操作维度：决策检索的步数与字符数**

| 任务 | 不使用系统 | 使用系统 | 提效 |
|:---|:---:|:---:|:---:|
| 查询"Q3 是否冻结发布" | 7 步（打开飞书 → 搜索群聊 → 滚动历史 → 翻 OKR → 翻文档 → 比对时序 → 形成结论） | 1 步（CLI 拦截卡片直接给出结论） | **86% 步数减少** |
| 输入"override deploy" 所需上下文 | ~120 字符（手写决策 ID + 来源 + 理由） | ~15 字符（`--override-decision=dec_xxx`） | **88% 字符减少** |
| 跨系统冲突自检 | 5 步手工巡检 | 0 步（系统自动推送卡片） | **100% 自动化** |

```
E_step = (steps_baseline - steps_system) / steps_baseline × 100%
```

**目标**：E_step ≥ 80%（参考赛题示例 80%）

### 6.2 支撑指标（验证系统稳定性）

| 编号 | 指标 | 公式 | 目标 |
|:---|:---|:---|:---:|
| S1 | 违规拦截率 | R_block = (N_before − N_after) / N_before × 100% | ≥ 95% |
| S2 | 误报率 | FAR = \|FP\| / (\|TP\| + \|FP\|) × 100% | ≤ 10% |
| S3 | Hot Path 延迟 | L_hot = t_cache_hit + t_rule_match | ≤ 200ms |
| S4 | Cold Path 延迟 | L_cold = t_seed2_extract + t_reflect + t_graph_hop | ≤ 3s |
| S5 | 自适应遗忘精准度 | P_decay = 1 − \|T_actual − T_predicted\| / T_actual | ≥ 80% |
| S6 | 主动确认有效率 | E_confirm = N_confirmed_correct / N_confirm_cards_pushed × 100% | ≥ 75% |

**评测设计原则**：三大主测试是**赛题强制项**，必须 100% 覆盖；支撑指标用于侧面证明系统稳定与体验。答辩时主推三大主指标，支撑指标作为追问储备。

### 场景五：决策原子全生命周期演示（端到端叙事）

本场景串联感知-决策-记忆三环，展示一条决策从诞生到归档的完整生命周期。

**背景**：系统已存在决策 A：`(项目X, RELEASE_DATE, 2026-05-01)`，provenance=USER_STATED，confidence=0.95，状态 ACTIVE。

```
T+0d   群聊新消息："项目X上线时间调整到5月15号"
       → 感知环：Cold Path 提取候选决策 B
         (项目X, RELEASE_DATE, 2026-05-15)
       → 精确索引命中决策 A，触发演化判定

T+0d   Doubao 演化判定：B SUPERSEDES A，confidence=0.72
       → 决策环:confidence 处于边界区间 [0.5, 0.85]，触发 Reflect
       → Reflect 评估：单源信号、无审批确认、quality_score=0.65
       → 决策标记为 HYPOTHESIS（暂不覆写 A）
       → uncertainty=0.45，未达卡片推送阈值 0.7

T+3d   跨系统扫描：飞书 OKR 仍显示 "Q2 项目X 5/1 上线"
       → uncertainty 因跨源不一致 +0.15 → 0.60
       → 仍未达阈值，继续观察

T+10d  时间衰减：B 未获新证据，A 未被验证
       → uncertainty 衰减后 = 0.78 ≥ 0.7 → 触发卡片
       → 闸门校验：当日预算剩余 3 次 ✓ 当前 14:30 工作时段 ✓
       → 推送确认卡片至张三（决策负责人）

T+10d  张三反馈：确认 B
       → 记忆环：A 状态 ACTIVE → ARCHIVED
       → B 状态 HYPOTHESIS → ACTIVE，confidence 提升至 0.95
       → 演化图谱新增边：B --SUPERSEDES--> A
       → Hot Path 缓存刷新，OKR 同步推送更新建议
       → 飞书 Bot 群聊通告："项目X 上线日期已更新为 2026-05-15"

T+11d  下游验证：CLI 部署命令查询时直接返回 B
       OKR 系统收到对齐建议卡片
       文档同步检查发现 ARCH-003 仍写 5/1，推送文档更新提醒
```

**本场景同时验证的指标**：抗干扰召回（10 天后仍能精确匹配）、矛盾覆写准确率（B SUPERSEDES A）、跨系统对齐（OKR+文档协同更新）、五维遗忘（uncertainty 随时间与跨源信号联动）、打扰闸门（工作时段 + 预算检查）。

> **设计原则**：v3.3 把 Doubao 与飞书 API 的有限配额作为**一等约束**纳入架构，并在产品层引入打扰预算与工作时间窗，避免系统沦为骚扰小红点。在这种约束下：
> - Hot/Cold 双路径不是优化项，而是**必然结构**——95% 请求由 Hot Path 零 LLM 服务。
> - 跨系统对齐只在精确索引命中后触发，避免无差别 API 扫描。
> - Reflect 仅对边界置信度调用，把额度花在真正需要语义判断的场景。
> - LLM 校准超参在离线时段完成，不挤占在线服务额度。
> - 卡片推送经过预算与时间窗双闸门，把"主动性"与"侵入性"分离。
>
> 这一框架使系统在赛事资源下可跑通，也使其在真实企业部署时具备**经济可行性与用户可接受性**——这是评委追问"产品化路径"时的最强答案。

## 十一、实施路径

### 11.1 技术栈选型

| 模块 | 选型 | 理由 |
|:---|:---|:---|
| LLM 服务 | Doubao 2.0（heavy）+ Doubao 1.6（light）+ Doubao Embedding v1 + 本地 7B 量化降级（W12） | 主路径精度，降级保活 |
| 短期会话记忆 | LangMem Thread Context | 复用前沿框架 |
| 结构化存储 | PostgreSQL 16 | ACID + JSONB + 倒排索引 |
| 语义向量 | Qdrant | 高性能近邻检索 |
| 演化图谱 | Neo4j Community / Kuzu | 多跳推理 + 版本溯源 |
| 缓存层 | Redis 7 | Hot Path LRU + 5min TTL |
| 飞书集成 | 开放平台 SDK + Bot Webhook | 全源事件接入 |
| CLI 拦截 | OpenClaw Hook | 命令前/后钩子 |
| 后端服务 | FastAPI + Celery | 异步事件处理 |
| 任务调度 | v1: APScheduler（同进程内存调度，详见宪法 §3.3） / v2: Celery Beat | 定期衰减、Reflect 离线评估 |

### 11.2 三阶段交付里程碑

```

  ✓ Hot Path 精确索引检索
  ✓ 验收：单源决策提取准确率 ≥ 85%

Demo 2（动态闭环，第 3 周）
  ✓ 演化判定（SUPERSEDES/REFINES）
  ✓ 五维遗忘公式上线

  ✓ 打扰预算 + 工作时间窗闸门

Demo 3（全链路闭环，第 4 周）
  ✓ 跨系统一致性扫描（OKR + 文档 + 审批）
  ✓ Reflect 自改进循环
  ✓ CLI 决策拦截端到端联调
  ✓ 三大基准测试报告
  ✓ 验收：抗干扰召回 ≥ 90%，时间维度提效 ≥ 60×
